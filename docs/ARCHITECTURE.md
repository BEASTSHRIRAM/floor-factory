# THE FLOOR — System Architecture & Build Plan

**Event:** Vibe-a-thon (Geek Room × 2nd Brain Labs) · **Submission deadline:** 25 Nov 2026, 11:59 PM IST
**Product:** A Software Factory where agents are employees. They bid for work, get paid in compute credits, get reviewed, appeal rejections, get fired, and get replaced by mutated offspring. The *only* way any agent can touch a real system is by calling tools on a **Synapse-generated MCP server** — Synapse is not a garnish, it is the factory's hands.
**Stack:** LangGraph (Python) · Groq `openai/gpt-oss-120b` · Next.js mission-control UI · SQLite · Synapse CLI (`@2ndbrainlabs-ai/synapse-cli`, Node 20+)

**Track strategy (from the participant guide):** THE FLOOR is submitted as **Track 4 — Open Innovation** (the product is the factory, not a single copilot), but it is deliberately engineered to also satisfy the judging criteria of the set tracks:

- **Track 1 criteria:** agents complete ≥3 real multi-step tasks through an Auto-mode MCP server, with **zero changes to the target app's code**.
- **Track 2 criteria:** one Custom-mode composed "smart tool" (see §4.4), a hard **confirmation step before any data-changing tool call**, and visible error/edge-case handling.
- **Track 3 criteria:** two codebases → two MCP servers, and a **live `synapse build --discover` onboarding moment** in the demo (§4.5).

---

## 1. Design principles

1. **Money math is code, not LLM.** Ledger, payroll, firing thresholds, bid scoring are deterministic Python. LLMs write bids, plans, reviews, and termination-letter flavour text — never arithmetic.
2. **Every action is an auditable record.** A job's tool-call transcript is the work product the Reviewer grades. If it isn't in SQLite, it didn't happen.
3. **Writes are gated, reads are free.** Read tools execute immediately; write tools pass a confirmation gate (§4.3). This is both a safety story for judging and the demo's human-in-the-loop beat.
4. **One writer for money.** All ledger mutations go through a single service function inside a SQLite transaction. Agents never touch the DB directly.
5. **Demo determinism where it matters.** Job execution is genuinely agentic, but the demo dataset is seeded so the narrative beats (one rejection, one appeal, one firing) are statistically near-guaranteed, with a scripted-fallback "demo mode" for Manager/Reviewer narration if a live run goes off-script (§8).

## 3. LangGraph topology

Two graph levels: one **shift graph** (the factory's heartbeat) and three invoked subgraphs (worker execution, review, appeal review). All state is checkpointed; `thread_id = "floor-main"` for the shift graph, `thread_id = work_order_id` for worker subgraphs.

### 3.1 Shift graph (orchestrator)

```
START
  │
  ▼
intake ────────────── Manager scans target backlog (via read tools) +
  │                    seeded job briefs → creates jobs in `draft`
  ▼
price_and_post ────── Manager sets budget per job (rule-bounded LLM
  │                    suggestion, clamped by economy/ rules) → `open`
  ▼
collect_bids ──────── fan-out via Send() to `bid` node, one per
  │                    eligible active agent (parallel)
  ▼
award ─────────────── economy/ scoring: score = 0.45·reputation
  │                    + 0.30·confidence − 0.25·(price/budget)
  │                    → creates work_order, job → `awarded`
  ▼
execute ───────────── invokes Worker subgraph (§3.2) → job `in_review`
  │
  ▼
review ────────────── invokes Review subgraph (§3.3)
  ├── accept ───────► settle: ledger payment, reputation +, job `paid`
  └── reject ───────► appeal_window
                        ├── worker appeals ─► appeal_review (§3.3, blind)
                        │     ├── upheld ───► settle (pay + Reviewer-A rep hit)
                        │     └── denied ───► no pay, reputation −, job `failed`
                        └── no appeal ──────► no pay, reputation −, job `failed`
  │
  ▼
cycle_close ───────── CFO (deterministic): charge running costs for the
  │                    cycle, evaluate firing rule, fire/hire/mutate (§5)
  ▼
shift_report ──────── emits summary events to UI
  │
  └──► loop to intake until shift ends (job queue empty or cycle cap)
```

Jobs are processed **sequentially** through award→execute→review in v1 (concurrency is a stretch goal, §9 cut order). Bidding is parallel; execution is not — this keeps the demo legible and the ledger race-free.

### 3.2 Worker execution subgraph

```
plan ──► act ──► (tool is read)  ──► observe ──► act … (loop)
           │
           └──► (tool is write) ──► confirm_gate ──► act
                                      │ interrupt() — human or policy
                                      ▼
                              approved → execute tool
                              rejected → observe("confirmation denied")
verify ──► submit_work
```

- `plan`: worker LLM gets job brief, acceptance criteria, and its tool list (from `tools_registry` for the job's target system). Produces a short plan; stored on the work order.
- `act`/`observe`: ReAct-style loop over MCP tools, max 20 tool calls per job (hard cap in code; exceeding it auto-submits as-is). Every call is written to `tool_calls` *before* execution (intent) and updated with the result after.
- `confirm_gate`: for any tool classified `write`, the graph calls LangGraph `interrupt()` with the tool name, args, and job context. The API surfaces this as a pending approval; the UI shows the confirmation card (§7). Resume via `Command(resume={"approved": bool, "by": "human"|"policy"})`. Policy auto-approve exists but defaults **off for writes in demo mode** — the human confirmation is a judged feature, we show it.
- `verify`: worker must re-read system state through read tools and check each acceptance criterion; produces a per-criterion pass/fail checklist. This checklist + transcript is the submitted work product.
- `submit_work`: work order → `in_review`; emits UI events.

### 3.3 Review subgraph (used twice: primary + appeal)

- Input: job brief, acceptance criteria, worker's verify checklist, full `tool_calls` transcript.
- Reviewer agent (its own roster agent with a persona, paid a flat review fee from the job budget) outputs structured verdict: `severity ∈ {none, P3, P2, P1, P0}`, `verdict ∈ {accept, reject}`, rationale, per-criterion findings.
- **Blind appeal:** the appeal invocation constructs a *fresh state containing only* brief + criteria + transcript. Reviewer A's verdict, severity, and rationale are **excluded by construction** (the appeal state type doesn't have those fields), and the appeal reviewer is a different roster agent. If the appeal accepts, Reviewer A takes a reputation penalty and the CFO logs a `penalty` — this is what makes Reviewer A's reputation a real, losable asset.
- Appeal is allowed **once per work order**, costs the worker a small appeal fee (deducted win or lose — skin in the game, stops frivolous appeals).

### 3.4 Human interrupt points (complete list)

1. **Write-tool confirmation** (§3.2) — the routine gate.
2. **Final acceptance override** — optional: after Reviewer accept, a job flagged `requires_human_merge` (config, default ON for the demo's last job) waits for a human "Approve & close" click in the UI. This is the "human only merges" gate from the product concept.
3. Nothing else blocks on a human. Firing, hiring, payroll are fully autonomous — that's the point of the demo.

## 4. Synapse integration

### 4.1 How a worker's tool call flows

```
Worker node (LangGraph)
  → mcp_manager.call_tool(system_id, tool_name, args)
      → policy check: tools_registry.effect == write?
          → yes: confirm_gate interrupt (must already be approved
                 before this call is dispatched — enforced in §3.2)
      → MCP client session (stdio) → generated server process
          → generated tool performs HTTP call to target app API
      ← result (structured) → written to tool_calls → observe node
```

The LangGraph worker never imports target-app code and never sees a URL. Its entire world is the tool list Synapse generated. Swapping the target system = swapping `system_id`.

### 4.2 Hosted vs `--local` — decision: **`--local` with Groq, primary; one hosted build as hot spare**

| Factor | Hosted | `--local` (Groq) | Verdict |
|---|---|---|---|
| Output artifact | No file; config in Synapse account, served via `npx @2ndbrainlabs-ai/synapse-mcp` runner + `SYNAPSE_SERVER_ID` | A real Python file in the project root (`synapse_auto_server.py` / `<tool>_server.py`) | Local file = version-controlled, inspectable, restartable by our supervisor. **Local wins.** |
| Demo-time dependencies | Synapse cloud + npx fetch + our app + Groq | Our app + Groq only (server file already generated) | Fewer moving parts live. **Local wins.** |
| Quota | Free tier: 10 servers / 100k indexed lines — we'd use ≤3 servers, ~1k lines. Fine either way. | Never counted | Non-issue for our size; local still simpler. |
| Rebuild cost during the week | Rebuild of unchanged repo is free; discover is cheap | Free, unlimited iterations while tuning tool exposure | **Local wins** — we will rebuild a lot on Days 0–2. |
| Codegen quality risk | Synapse's own models | Depends on our model following a strict schema — guide warns small local models fail with `returned no emit_tool_plan call` | **The one real risk.** `gpt-oss-120b` is a strong schema-follower; Day 0 smoke test is the gate (§8). |
| Language constraint | Auto works for all supported languages | Local Auto **only writes a file for Python projects** | Our targets are Python/FastAPI → constraint doesn't bite. Another reason the demo apps are Python. |
| Privacy | Routes/docstrings leave the machine (fine — demo code) | Nothing leaves | Irrelevant here. |

**Plan:** generate both target servers with `synapse build --local` (Groq, `synapse model set groq`). Additionally produce **one hosted Auto build of TicketDesk** on Day 1 and keep its `SYNAPSE_SERVER_ID` config in the repo as a documented hot spare — if a local server file ever misbehaves in rehearsal, `mcp_manager` can be pointed at the hosted runner by config alone. The submission README documents both, which also evidences we actually explored Synapse's modes.

**Build flags (non-interactive, per the guide):**
- Auto: `synapse build --local --auto --endpoints "GET /tickets,POST /tickets,..."` with an explicit endpoint allowlist (fewer, well-named tools = better agent reliability, and judges reward deliberate exposure). Add `--smart-names` on the hosted spare only (it sends function details to the model — fine, but keep the primary path minimal).
- Secrets: target apps need no auth in the demo; if added later, headers go in as `${ENV}` placeholders per the guide — never hardcode.

### 4.3 The confirmation step (Track 2's judged safety criterion)

- `tools_registry.effect` is assigned at registration: HTTP-method-derived default (GET → read; POST/PUT/PATCH/DELETE → write), overridable per tool in a checked-in manifest (`targets/<app>/tools.manifest.json`) for cases like a POST search endpoint (read) or a GET that triggers a rebuild (write).
- The gate lives in the **worker subgraph** (§3.2), *before* `mcp_manager` dispatches. `mcp_manager` independently refuses any write call lacking a `confirmation_id` — defence in depth, so no code path can mutate a target system unconfirmed.
- Every confirmation (human or policy) is persisted on the `tool_calls` row: `confirmed_by`, `confirmed_at`, decision. The UI confirmation card shows: agent, job, tool, full args, and a plain-English "what this changes" line generated from the tool description.
- Demo policy: reads auto; **all writes human-confirmed**. A settings toggle (`POLICY_AUTO_APPROVE_WRITES`) exists for rehearsal speed but ships OFF.

### 4.4 The Custom-mode composed tool (Track 2 centrepiece)

TicketDesk also gets one Custom build:

```bash
synapse build --custom -q "resolve_ticket_end_to_end: given a ticket id, fetch the
ticket, classify its category and priority from its text, assign it to the right
queue, post an acknowledgement comment, and set status to in_progress"
```

- Output: `resolve_ticket_end_to_end_server.py` in the TicketDesk project — registered as a *second* MCP server for the same target system (`tools_registry.system_id` same, `server_kind = custom`).
- In THE FLOOR's fiction, this is **specialist equipment**: one worker archetype ("the veteran") is configured to prefer the composed tool; others use the raw endpoint tools. The job stats then show a real comparison — tool calls per job, success rate, cost per job, composed-tool worker vs raw-tool workers — which is exactly the one-tool-vs-many comparison Track 2 asks submitters to demonstrate, except ours emerges from the economy instead of a slide.
- The composed tool's internal writes still pass through the confirmation gate as a single unit (one confirmation for the composed action, with its sub-steps itemised on the card).

### 4.5 Live onboarding of a second codebase (`--discover` set piece)

Demo climax, rehearsed as a fixed procedure:

1. Presenter opens StockRoom code, adds one new endpoint live (pre-written snippet pasted in): `GET /items/low-stock?threshold=N`.
2. `onboarder` runs in `targets/stockroom/`: `synapse build --local --discover` (same flags as initial build + `--discover`; per the guide, only changed files are re-parsed and the same server identity is kept, so client config doesn't change).
3. `mcp_manager` restarts/refreshes that system's session, re-lists tools → the new tool appears in `tools_registry` → UI event `system.tools_updated` → the org chart shows StockRoom gaining a capability badge.
4. Manager immediately posts a job that *requires* the new tool ("Produce a reorder list for everything below threshold"), workers bid, one executes it.
5. Total elapsed target: < 90 seconds. Fallback if `--discover` is slow on the day: the endpoint is also present in a pre-built spare copy; we demo the tool appearing via registry refresh and are honest in the write-up about which path ran (the recorded demo video, shot Day 5, uses the genuine live path).

## 5. Data model (SQLite, `floor.db`)

All timestamps UTC ISO-8601. All money in integer **credits (₡)** — no floats anywhere near the ledger.

### agents
`id, name, persona_prompt, model, tier (junior|senior|veteran), base_salary_credits, risk_appetite (0..1), status (active|fired), parent_agent_id → agents.id NULL, generation INT, mutation_note TEXT, reputation REAL (0..100, denormalised cache), created_at, fired_at, fire_reason`
- Lineage: a hire created by mutation has `parent_agent_id` = the fired (or top-performing donor) agent, `generation = parent.generation + 1`, and `mutation_note` describing the single mutated dimension (prompt trait, model, or risk_appetite ±).

### target_systems
`id, name, repo_path, api_base_url, status (online|offline)`
### mcp_servers
`id, system_id → target_systems, kind (auto_local|auto_hosted|custom_local), entry_point (file path or hosted server id), status`
### tools_registry
`id, mcp_server_id → mcp_servers, tool_name, description, effect (read|write), requires_confirmation BOOL` — unique `(mcp_server_id, tool_name)`; refreshed on discover, never deleted (tools that vanish are marked `retired`).

### jobs
`id, system_id → target_systems, source (seeded|backlog_scan|live_demo), title, brief, acceptance_criteria (JSON list of checkable statements), budget_credits, status (draft|open|bidding|awarded|executing|in_review|appealed|paid|failed), requires_human_merge BOOL, created_cycle, created_at`
### bids
`id, job_id → jobs, agent_id → agents, price_credits, confidence REAL (0..1), rationale, created_at` — `UNIQUE(job_id, agent_id)`.
### work_orders
`id, job_id → jobs, agent_id → agents, agreed_price_credits, plan TEXT, status (working|submitted|accepted|rejected|appeal_accepted|appeal_rejected), started_at, finished_at` — at most one work order per job reaches a paid state.
### tool_calls  *(the audit transcript)*
`id, work_order_id → work_orders, tool_name, args_json, effect, confirmation_id NULL, confirmed_by (human|policy) NULL, confirmed_at NULL, status (proposed|confirmed|denied|executed|error), result_summary, error TEXT NULL, created_at`
### reviews
`id, work_order_id → work_orders, reviewer_agent_id → agents, kind (primary|appeal), severity (none|P3|P2|P1|P0), verdict (accept|reject), rationale, findings_json, created_at`
### appeals
`id, work_order_id → work_orders, agent_id → agents, fee_credits, status (pending|upheld|denied), appeal_review_id → reviews NULL, created_at` — max one per work order (unique index).
### ledger  *(append-only)*
`id, agent_id → agents, kind (earning|review_fee|appeal_fee|running_cost|tool_cost|bonus|penalty), amount_credits (signed INT), balance_after INT, ref_type, ref_id, cycle_no, note, created_at`
### payroll_cycles
`id, cycle_no, opened_at, closed_at, summary_json`
### reputation_events
`id, agent_id → agents, delta REAL, reason, ref_type, ref_id, created_at` — `agents.reputation` is a cache recomputed from these.
### events  *(UI stream / replay)*
`id, seq AUTOINCREMENT, type, payload_json, created_at` — every UI-visible happening is written here first, then pushed over SSE; a reconnecting UI replays from `seq`.

### Key invariants (enforced in `economy/`, tested)
1. **Ledger is append-only.** No UPDATE/DELETE on `ledger`; corrections are new rows. `balance_after` must equal the agent's previous `balance_after + amount_credits` — checked inside the transaction.
2. **Payment only on accept.** `earning` rows are created exclusively by the settle path (primary accept or appeal uphold). Rejection creates no earning; the appeal fee is charged regardless of outcome.
3. **One active work order per agent; one paid work order per job.**
4. **No write without confirmation.** `tool_calls` rows with `effect = write` cannot reach `executed` with `confirmation_id NULL` — enforced in `mcp_manager` *and* by a DB CHECK.
5. **Fired agents are inert.** `status = fired` agents cannot bid, review, or be awarded; the bid fan-out filters on `status = active`.
6. **Firing rule (deterministic):** at cycle close, for each active agent: if net over the **last 2 closed cycles** (earnings − running costs − tool costs) < 0 **and** the agent completed ≥1 work order in that window → fired. New hires get a 2-cycle grace period (rule can't fire them before they've had the same window).
7. **Reputation is bounded and derived.** Clamped 0..100; deltas only from: accept +4, reject −6, appeal upheld (worker +3, Reviewer A −8), P0/P1 review issued by a reviewer whose verdict is later overturned −8, guardrail-style policy violation (denied confirmation ignored — can't happen; unconfirmed write attempt) −15.
8. **Mutation is single-dimension.** A child differs from its parent in exactly one of {persona trait, model, risk_appetite}; `mutation_note` must say which. Keeps the "evolution" claim honest and the demo narration truthful.

## 6. Demo target codebase — "TicketDesk" (+ "StockRoom")

### 6.1 TicketDesk (primary target; build time ≈ half a day)

A deliberately ordinary FastAPI support-ticket API — the kind of internal tool every company has. ~600 LOC, one file plus a seed script, its own SQLite file. **THE FLOOR never modifies this code; agents only call its API through MCP tools.**

Endpoints (the Synapse Auto allowlist — 11 tools, deliberately not all routes):

| Method & path | Effect | Why exposed |
|---|---|---|
| `GET /tickets?status=&assignee=&priority=` | read | Core work surface |
| `GET /tickets/{id}` | read | Verification |
| `GET /tickets/duplicates` | read | Powers the dedupe job |
| `POST /tickets/{id}/assign` | write | Triage jobs |
| `POST /tickets/{id}/priority` | write | Triage jobs |
| `POST /tickets/{id}/comment` | write | Escalations, acknowledgements |
| `POST /tickets/{id}/status` | write | Closures |
| `POST /tickets/merge` | write | Dedupe job |
| `GET /sla/breaches` | read | SLA job |
| `GET /stats/summary` | read | Manager's intake scan + verify step |
| `POST /tickets` | write | Demo reset / live job creation |

Not exposed: user admin, delete endpoints (hard delete is un-agentable by design — a point we make in the write-up: *exposure is a safety decision*).

**Seed data:** 25 tickets with planted messiness — 6 unassigned (2 of them P1), 4 duplicates of 2 originals, 5 stale `resolved` tickets never closed, 3 SLA-breached, inconsistent categories (`billing`, `Billing`, `billng`), 2 tickets with angry-customer text requiring escalation comments.

**Seeded job families** (each with machine-checkable acceptance criteria the worker's `verify` node can test via read tools):

1. **Triage the unassigned queue** — every unassigned ticket gets an assignee + sane priority. *Criteria: `GET /tickets?assignee=none` returns 0.*
2. **Merge the duplicates** — duplicate groups merged into canonical tickets. *Criteria: `GET /tickets/duplicates` returns empty.*
3. **Close the stale resolved** — verify resolution comment exists, then close. *Criteria: no ticket in `resolved` older than 7 days.*
4. **SLA breach report + escalation** — comment an escalation on each breached ticket and produce the breach list. *Criteria: every breached ticket has ≥1 escalation comment.*
5. **Normalise categories** — fix the category mess to the canonical set. *Criteria: distinct categories ⊆ canonical list.*

### 6.2 StockRoom (second target; ≈250 LOC, built Day 4)

Tiny inventory API: `GET /items`, `GET /items/{id}`, `POST /items/{id}/adjust`, `GET /orders/pending`. Initially onboarded with 3 read tools only. The live demo adds `GET /items/low-stock` + `--discover` (§4.5). Seeded with 15 items, 4 below threshold.

## 7. UI spec — Mission Control (Next.js)

Single page, dark "trading floor" theme. **Data flow:** on load, REST snapshots (`/state/agents`, `/state/jobs`, `/state/ledger?limit=100`, `/state/cycle`); then one SSE connection to `/events?from_seq=N` drives a client-side reducer. Every panel below is a pure function of snapshot + event stream — no polling.

Layout (3 columns + header + bottom strip):

- **Header bar:** factory name, current cycle #, shift clock, treasury totals: credits paid out, jobs completed/failed, active agents count. A red **PAYROLL** banner flashes here at cycle close.
- **Left — Org Chart ("The Floor"):** agent cards in a grid: name, tier badge, model, generation (`Gen 2`), reputation bar, credit balance, live status chip (`idle / bidding / working / in review / FIRED`). Working agents show their current job + latest tool call in miniature. **Firing moment:** card shakes, stamps "TERMINATED", slides down to **The Graveyard** strip at the bottom of the column; the replacement card drops in at the top with a "NEW HIRE — Gen N+1" pulse and its `mutation_note` as a subtitle ("inherited Nova's playbook; mutated: bids 15% more aggressively"). Reviewer agents sit in a visually separate "management" row.
- **Centre — Job Board:** columns `Open → Bidding → In Progress → In Review → Done`. Job cards show title, target system, budget ₡, and (in Bidding) the live bid stack. **Bid ticker:** a stock-ticker strip across the top of this column — every bid event scrolls: `PIXEL bids ₡42 (conf 0.81) on "Merge duplicates"`. Clicking a job opens a drawer with brief, acceptance criteria, bids table, the full tool-call transcript, verify checklist, and review/appeal history.
- **Right — Ledger & Narration:** top half, the **ledger feed**: every credit movement, signed and colour-coded, with its reason (`+₡120 earning — Triage job accepted`, `−₡18 running cost — cycle 3`). Bottom half, the **narration log**: plain-English event lines ("Manager posted 'SLA breach report' at ₡150", "Reviewer rejected Maya's work — P1: closed a ticket without a resolution comment", "Maya is appealing…", "APPEAL UPHELD — Reviewer penalised").
- **Confirmation modal (the human gate):** overlays centre screen whenever a write confirmation is pending: agent avatar/name, job title, tool name, itemised args, "what this changes" line, Approve / Deny buttons, and a countdown-free design (no auto-timeout — a human decision shouldn't expire mid-demo). Denials feed back to the worker as an observation it must adapt to. Pending confirmations also queue as a badge in the header so none is ever missed.
- **Payroll overlay:** at cycle close, a modal table counts through each agent: earnings, costs, net, verdict — `SAFE` / `ON NOTICE` (one bad cycle) / `FIRED` — then fires/hires animate in the org chart. Dismissed by click; also auto-dismisses after the last firing animation.

**Event types streamed (from `events` table):** `job.posted, bid.placed, job.awarded, tool.proposed, tool.confirmation_requested, tool.executed, work.submitted, review.completed, appeal.filed, appeal.decided, payment.made, cycle.closed, agent.fired, agent.hired, system.tools_updated, narration` (catch-all human-readable line).

## 9. Minimum demoable slice + cut order

**Minimum slice (the demo still tells the whole story):**
Manager posts 3 seeded TicketDesk jobs → 3+ workers bid live → award → worker executes through Synapse MCP tools with **one human-confirmed write** → Reviewer accepts 2, rejects 1 → ledger pays the accepted, starves the rejected → org chart + job board + ledger update live. Payroll/firing can be *narrated from one pre-run cycle* if the live cycle close isn't ready.

**Cut order (cut from the top; each cut keeps the slice intact):**
1. **Appeal flow** — rejections become final; Reviewer reputation still tracked. (Biggest single saving.)
2. **Mutation lineage** — fired agents are replaced by fresh static personas; drop `parent_agent_id` storytelling.
3. **Live `--discover` onboarding** — StockRoom ships pre-onboarded; the two-system story remains, the live moment becomes a recorded clip in the video.
4. **Custom composed tool** — all workers use raw Auto tools; Track 2 angle rests on the confirmation gate alone.
5. **UI theatre** — bid ticker, payroll overlay, graveyard animations → plain feeds and tables. Data panels stay.
6. **Backlog-scan intake** — Manager posts only seeded jobs (already the fallback for `source`).
7. **Multi-cycle payroll** — one cycle close only, triggered manually by the presenter.

**Never cut:** the confirmation gate (judged + it's the safety story), the ledger (it's the product's memory), real MCP execution against the real target app (no mocked tool results — the moment tool calls are faked, the submission's core claim dies).

## 10. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Groq `--local` codegen fails (`emit_tool_plan`) | Day 0 gate; hosted-build fallback decided same day (§8). |
| Groq rate limits during demo | Pacing between LLM calls; bids/narration on `gpt-oss-20b` flag; demo video recorded Day 5 as insurance. |
| Synapse hosted spare needed but quota/account issue | We need ≤3 servers of a 10-server free tier; create the spare Day 1, not in a panic on Day 5. |
| Worker LLM loops or produces garbage tool args | Hard 20-call cap; tool-arg validation errors returned as observations (agent self-corrects); verify checklist exposes failure honestly to the Reviewer instead of hiding it. |
| Demo beats don't land (no rejection/firing in the live run) | Seed one worker persona to be sloppy (skips verification comments → near-certain P1 rejection) and one to be expensive (high salary, low bids → near-certain negative net by cycle 2). Determinism through roster design, not scripted outputs. |
| MCP server process dies mid-demo | `mcp_manager` supervisor with restart + tool re-list; target apps are stateless-per-request so a restart loses nothing. |
| Scope creep | §9 cut order is pre-agreed; feature freeze 24 Nov 18:00; code freeze 25 Nov 12:00 except submission-breaking fixes. |
